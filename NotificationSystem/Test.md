# 3. Test Notification Creation

### API 2 – Create Email Notification

**Method:** POST

**URL:**

```http
http://localhost:8080/api/v1/notifications
```

**Headers:**

```http
Content-Type: application/json
```

**Request Body:**

```json
{
  "sourceService": "ORDER-SERVICE",
  "recipientId": "USER-1001",
  "channel": "EMAIL",
  "destination": "testuser@example.com",
  "eventType": "ORDER_CONFIRMED",
  "templateCode": "ORDER_CONFIRMATION",
  "idempotencyKey": "ORDER-1001-EMAIL-001",
  "payload": {
    "customerName": "John",
    "orderId": "ORD-1001",
    "amount": 2500,
    "currency": "INR"
  }
}
```

### Expected response

```json
{
  "notificationId": "<generated-uuid>",
  "status": "PENDING",
  "message": "Notification created successfully"
}
```

The notification ID is generated by the application.

Save this ID for the remaining API tests.

### What to verify in PostgreSQL

Connect to the Docker PostgreSQL database:

```cmd
docker exec -it notificationsystem-postgres-1 psql -U postgres -d notification_db
```

Check notification:

```sql
SELECT *
FROM notification
ORDER BY created_at DESC;
```

Check outbox event:

```sql
SELECT *
FROM outbox_event
ORDER BY created_at DESC;
```

Expected:

**Notification table**

- New notification record exists.
- Channel = EMAIL.
- Status = PENDING.
- Destination = testuser@example.com.
- Idempotency key = ORDER-1001-EMAIL-001.

**Outbox event table**

- Corresponding outbox record exists.
- Event type = NOTIFICATION_CREATED.
- Status initially NEW, then PUBLISHED after successful publishing.

Note: Your actual table names may differ if you configured custom JPA table names.

| Routing key | Destination queue |
|---|---|

# 10. Test Idempotency

### Scenario

Send the same POST request again with the same:

- sourceService
- idempotencyKey
- channel

Use the same request body from API 2.

Expected response:

```json
{
  "notificationId": "<same-existing-uuid>",
  "status": "SENT",
  "message": "Notification already exists"
}
```

The returned status depends on the existing notification's current status.

Verify:

1. Same notification ID is returned.
2. No second notification record is created.
3. No second outbox event is created.
4. No duplicate email is sent.

Check database:

```sql
SELECT *
FROM notification
WHERE source_service = 'ORDER-SERVICE'
  AND idempotency_key = 'ORDER-1001-EMAIL-001'
  AND channel = 'EMAIL';
```

Expected: one matching record.

# 15. Test Retry Mechanism

**Objective:** Verify that a failed message is retried instead of being immediately discarded.

Before testing, confirm that the email consumer propagates processing exceptions to the RabbitMQ listener container. If exceptions are swallowed, configured retries will not be triggered.

### Failure scenario

1. Stop Mailpit:

```cmd
docker compose stop mailpit
```

2. Submit a new email notification with a unique idempotency key.
3. Check application logs:

```cmd
docker compose logs -f notification-service
```

4. Observe email consumer failures and retry attempts.

5. Check the notification status and RabbitMQ queue.

Expected behavior:

- Email sending fails because SMTP is unavailable.
- The configured retry policy attempts processing again.
- If retry attempts are exhausted, the message is rejected without requeueing.
- RabbitMQ routes the message to the email DLQ, provided the DLX configuration is correct.

Restart Mailpit:

```cmd
docker compose start mailpit
```

**Important:** This test depends on the actual retry policy, listener configuration, and exception propagation implemented in the project. Confirm these before treating the test as passed.

```text
notification.email.dlq
```

After exhausting retries for the failed email message, verify:

- The message appears in the email DLQ.
- The original queue no longer contains that failed message.
- The dead-letter exchange and routing key are correct.

Repeat the same type of failure test for SMS and push only if their consumers have retryable failure scenarios configured.

Do not mark DLQ testing as successful until you have observed an actual failed message arriving in the DLQ.
